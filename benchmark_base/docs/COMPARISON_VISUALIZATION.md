# Comparison and visualization workflow

This document describes the post-processing path for an existing benchmark run. The goal is to separate expensive ROS/bag processing from lightweight result inspection and to keep every report grounded in the selected run rather than historical constants.

## One-command comparison

```bash
benchmark_base/bin/lio-benchmark compare --run /path/to/run
```

The default command is lightweight after standardized trajectories exist. It generates or refreshes:

- `metrics/full_comparison.json`
- `reports/full_comparison.md`
- `figures/comparison_dashboard/trajectory_xy_overlay.png`
- `figures/comparison_dashboard/trajectory_z_drift.png`
- `figures/comparison_dashboard/diagnostic_dashboard.png`
- `figures/comparison_dashboard/relative_to_baseline.png`
- `figures/resource_curves/resource_curves.png`
- `figures/resource_curves/resource_summary.png`
- `figures/resource_curves/resource_summary_valid.png`
- `metrics/trajectory_discontinuity.json`
- `metrics/trajectory_discontinuity/<algorithm>.csv`
- `reports/trajectory_discontinuity.md`
- `figures/trajectory_discontinuity/position_step.png`
- `figures/trajectory_discontinuity/yaw_step.png`
- `reports/comprehensive_comparison.{json,md,csv}`

`compare` always refreshes the canonical comparison first, then renders trajectory/resource figures, computes trajectory discontinuity diagnostics and finally generates the comprehensive report from the current run only.

The active comprehensive report is generated by `evaluators/current_run_report.py`. It does not use the historical ten-algorithm recommendation template. Whole-run relative RMSE/P95 are recomputed from the current `standardized/trajectories/*.csv`; if a current-run metric or map artifact is missing the report emits `N/A` rather than filling it from an older run.

Trajectory lifecycle/health and map health are independent. Before map reconstruction, a lifecycle `SUCCESS` with empty trajectory-health flags can enter the shortlist. After current-run map metrics exist, an explicit map-health failure also removes that algorithm from `recommendation_eligible`. Missing map data does not itself count as a map-health failure.

## Lightweight visualization only

```bash
benchmark_base/bin/lio-benchmark visualize --run /path/to/run
```

If `metrics/full_comparison.json` already exists, this does not replay the trajectory bags. It uses standardized CSV trajectories and existing resource-monitor outputs.

The default trajectory figures only show algorithms whose lifecycle status is `SUCCESS` and whose trajectory health flags are empty. Diverged or incomplete algorithms remain available in the `*_all.png` figures so failures are not hidden but also do not destroy the scale of paper-facing plots.

The XY overlay uses initial yaw + translation alignment to the selected baseline. This is a relative diagnostic visualization. Without independent ground truth it must not be interpreted as ATE/RPE or absolute accuracy.

Select another baseline when needed:

```bash
benchmark_base/bin/lio-benchmark visualize \
  --run /path/to/run \
  --baseline glim_odometry
```

## Trajectory discontinuity timeline

`trajectory_discontinuity.py` is ROS-free and consumes only the standardized trajectory CSVs. For each consecutive pose sample it records:

- sensor timestamp;
- bag-relative time when current-run `bag_analysis.json` exposes the LiDAR `header_first_s`;
- `dt_s`;
- position step `Δp`;
- yaw step `Δyaw` after unwrap;
- speed and yaw rate;
- current XYZ position.

The per-trajectory jump thresholds are robust diagnostics:

- position: `max(0.5 m, median + 10 * 1.4826 * MAD)`;
- yaw: `max(10 deg, median + 10 * 1.4826 * MAD)`.

When bag timing evidence is unavailable, the timeline falls back to the selected baseline's first standardized timestamp and records that provenance explicitly.

`position_step.png` and `yaw_step.png` show all available algorithms against the same bag-relative time axis. Marked jumps are diagnostic only. A full-SLAM loop correction can be a real pose jump and is not automatically treated as a trajectory-health failure.

The complete per-step CSVs are intentionally retained because they form the time-series backend for a future interactive viewer: selecting one timestamp can later highlight the corresponding trajectory position, nearby point cloud, resource load and phase state without changing these metric definitions.

## Resource figures

`resource_curves.png` keeps the full process-tree time series for CPU, RSS and thread count. CPU 100% means one logical CPU core. Do not interpret a low average CPU value as efficiency when the corresponding trajectory has failed or terminated early.

`resource_summary.png` keeps all algorithms and marks rows with trajectory health failures. `resource_summary_valid.png` excludes those health-fail algorithms for selection-oriented comparison. Every panel uses algorithm labels on the x-axis.

The summary CPU panel reports three statistics derived from the recorded `sample_history`:

- `median_cpu_percent`: typical process-tree scheduler demand;
- `mean_cpu_percent`: average demand across the run;
- `p95_cpu_percent`: sustained high-load envelope less sensitive to one instantaneous spike than peak CPU.

The raw `peak_cpu_percent` remains in `resource_summary.json` and `resource_summary.csv` for scheduler/headroom diagnosis.

For phase-specific CPU/RSS interpretation use `lio-benchmark phase-analysis`. New runs with valid clock anchors plus recorded/header timing evidence can reach `strict/clock-anchored`; runs without sufficient timing evidence explicitly downgrade rather than fabricating synchronized resource metrics.

## Optional map reconstruction and quantitative comparison

Map reconstruction is intentionally opt-in because it re-reads the raw LiDAR bag and can be expensive for long MID360 datasets. It does **not** rerun any LIO algorithm.

```bash
benchmark_base/bin/lio-benchmark compare \
  --run /path/to/run \
  --with-maps \
  --scan-step 5 \
  --point-step 20 \
  --voxel 0.12
```

The map path has three bounded steps:

1. `reconstruct_comparison_maps.py` discovers every current-run algorithm that has a standardized CSV, including a failed/crashed partial trajectory when one exists.
2. `visualize_baseline_maps.py` reconstructs each PLY from the same raw LiDAR samples, the manifest LiDAR-to-IMU extrinsic and the corresponding standardized trajectory.
3. `enhance_map_comparison.py` reads those current-run PLYs, computes quantitative consistency diagnostics and renders shared-scale comparison figures.

For every map the enhanced metrics include:

- raw XYZ extent (`max-min`) for audit;
- robust XYZ extent (`P99-P1`) to suppress isolated outliers;
- baseline-relative voxel occupancy IoU using a comparison voxel of at least `0.5 m`;
- symmetric nearest-neighbour mean/RMSE/P95/max distance on deterministic bounded samples;
- independent `map_health_flags` and `map_health_pass`.

Current conservative map-health flags are:

- `excessive_robust_z_span`: robust candidate Z span exceeds `2x` baseline robust Z span;
- `low_baseline_voxel_iou`: voxel IoU `< 0.10`;
- `high_symmetric_nn_p95`: symmetric NN P95 `> 2.0 m`.

These thresholds are engineering diagnostics, not absolute map-accuracy acceptance criteria.

Outputs under `figures/fast_livo2_baseline_maps/` include:

- `<algorithm>_map.ply`
- `<algorithm>_map_views.png`
- `trajectory_baseline_comparison.png`
- `map_comparison_xy.png` — trajectory+map-health-valid algorithms only, shared XY limits/Z scale
- `map_comparison_xz.png` — trajectory+map-health-valid algorithms only, shared XZ limits/Z scale
- `map_comparison_xy_all.png` — all available reconstructed maps, including failures/map-health-fail cases
- `map_comparison_xz_all.png` — all available reconstructed maps, including failures/map-health-fail cases
- `map_comparison_metrics.json`
- `map_comparison_metrics.md`
- `visualization_metadata.json`

The shared scales are important: each panel in one figure uses the same projection limits and the same Z normalization, so one algorithm cannot look artificially clean merely because Matplotlib auto-scaled its panel independently.

The PLYs remain usable in the existing benchmark viewer for interactive 3D inspection.

## Future interactive comparison frontend

The interactive frontend is deliberately deferred until the core metrics are stable. The intended frontend will consume existing artifacts rather than invent new metric paths:

- center/left: algorithm trajectory and reconstructed map/point-cloud views;
- right: CPU/RSS/thread and summary charts;
- bottom/shared timeline: bag-relative time with discontinuity events, phase boundaries and resource spikes;
- selecting/highlighting one time instant: highlight the algorithm pose, nearby raw LiDAR points and synchronized diagnostic/resource values;
- snapshot/export: preserve the selected timestamp, algorithms, anomaly reason and current metric values for experiment records.

The current core outputs already preserve sensor timestamps and provenance needed for this later layer. Exact per-sample resource-to-sensor-time export can be added as the final backend contract before implementing the UI.

## Individual stages

```bash
benchmark_base/bin/lio-benchmark standardize --run /path/to/run
benchmark_base/bin/lio-benchmark evaluate --run /path/to/run
benchmark_base/bin/lio-benchmark visualize --run /path/to/run
benchmark_base/bin/lio-benchmark report --run /path/to/run
```

`standardize` and `evaluate` currently share the canonical `summarize_smoke_run.py` pass because trajectory extraction, cleanup, diagnostic metrics and resource summary are produced together.

`report` runs `current_run_report.py`. It does not require map reconstruction; missing map artifacts remain `N/A`.

Use `--dry-run` on any stage to inspect the exact subprocess plan before execution.

## Output semantics

- Baseline-relative trajectory RMSE/P95 use initial yaw + translation alignment and are `relative-to-baseline/diagnostic/non-ground-truth` when no independent ground truth exists.
- Map IoU/nearest-neighbour values are baseline-relative map-consistency proxies, not absolute map accuracy.
- `path_length_m`, trajectory `z_range_m` and endpoint displacement are diagnostic health signals, not absolute accuracy metrics.
- Raw map Z extent is not trajectory Z drift; use robust map extent plus trajectory metrics separately.
- CPU 100% means one logical CPU core in the existing resource monitor.
- Peak RSS is process-tree resident memory when the monitor data is available.
- A very large path length can dominate linear plots; health-gated primary figures and `*_all` diagnostics prevent failed trajectories from destroying the selection-facing scale.
- Map reconstruction compares how the same raw LiDAR points are projected by different trajectories; it does not measure each algorithm's internal mapping implementation or provide an absolute map-quality score.
